### P0-5 流式聊天不落库（架构决策必须先定）

- **现状**：聊天流式直连 Python `/api/v1/ai/chat(langchain)/stream`，回复完成后**只写前端 localStorage**；Java `POST /api/v1/chat/conversations/{id}/messages` 是非流式的另一条路径，且会再调一次 Python `/api/v1/ai/chat`。两条链路互不相通。

- **收敛动作（推荐方案 A）**：
  - **方案 A（推荐）**：流式仍由前端直连 Python（保证逐字体验与降级链不变），但**流结束后前端调用 Java `POST .../messages` 把 user+assistant 消息落库**；Java 的 `sendMessage` 中"调 AI 生成"分支改为可选（`generate=false` 时仅落库）。
  - 方案 B：Java 增加 SSE 透传端点（`StreamingResponseBody`），前端只对 8080 发起，鉴权与落库都在 Java 闭环——多一跳延迟与实现成本，作为二期演进。
- **验收**：刷新页面/换设备后，聊天历史从 MySQL 恢复，与前端看到的一致。

### P0-7 头像与聊天图片无法落库（架构级缺口）

- **现状**：
  - `schema.sql:19` `companion.avatar VARCHAR(500)`，而前端 `CreatePage.vue` 的 avatar 是 **base64 data URL**（`compressImageFileToDataUrl` 压缩到 512px / quality 0.86，通常 50–150KB），`POST /companions` 会插入失败或截断。
  - `schema.sql:54-62` `message` 表**没有 images 列**，而前端 `Message.images` 是 base64 数组（`ChatPage.vue:163-171` 整屏渲染）。图片消息落库必丢。
  - `ChatServiceImpl.sendMessage` 只写 `content`，`ConversationDetailResponse.MessageResponse` 也只有 `role` / `content` / `createdAt`。
  - Java 端**没有任何文件上传或静态资源能力**（无 upload 目录、无 `addResourceHandlers`）。
- **问题**：这是任务五（头像代理）和任务四（消息落库）的硬阻断。任务五做完 AI 头像代理，用户自传的头像仍然存不进去；任务四做完消息落库，带图的消息刷新后图没了。
- **收敛动作（已决策：Java 加统一上传端点，只存 URL）**：
  1. Java 新增 `POST /api/v1/uploads`：收 `{ dataUrl }`（base64），解码后按 `{yyyyMM}/{uuid}.{ext}` 写到 `uploads/` 目录，返回 `{ url }`（形如 `http://localhost:8080/uploads/2026-11/xxx.jpg`）；
  2. `WebConfig` 加 `addResourceHandlers`，把 `/uploads/**` 映射到本地目录；`application.yml` 加 `app.upload.dir` 可配置；
  3. `message` 表加 `images TEXT`（存 URL 的 JSON 数组字符串），`Message` 实体、`ConversationDetailResponse.MessageResponse`、`ChatServiceImpl` 落库/读取同步；
  4. `companion.avatar` **不改列宽**（保持 VARCHAR(500)），因为存的是 URL 而不是 base64；前端在提交伴侣前先把 avatar 上传换成 URL；
  5. 前端 `lib/api.ts` 增加 `uploadImage(dataUrl)` 辅助函数，`CreatePage.vue`、`ChatPage.vue` 落库前调用。
- **验收**：创建伴侣后自传头像可跨设备访问（URL 能直接打开）；聊天发图 → 刷新页面图片仍在；MySQL `message.images` 是 URL 数组而非 base64。
- **二期**：对象存储（OSS / S3）替换本地目录，只需换 `FileService` 实现，接口不变。
