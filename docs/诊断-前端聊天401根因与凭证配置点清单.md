### 1.4 失败发生在哪一环

```
前端 3000 ──X-Service-Token(14字符)──► 5000
                                        └─ verify_service_token 比对失败 → 401
                                           （请求体根本没被处理，未触达 8002 / 智谱）
```

`backend/main.py:118-126`：

```python
def verify_service_token(x_service_token: Optional[str] = Header(None)):
    if not SERVICE_TOKEN:
        return
    if x_service_token != SERVICE_TOKEN:
        raise HTTPException(status_code=401, detail="Invalid or missing X-Service-Token")
```

该函数以 `Depends()` 挂在 `main.py:552` 与 `main.py:789` 两个流式端点。依赖注入先于 body 校验执行，所以表现为 401 而非 400/422。

前端 `useStreamingChat.ts` 收到 401 后抛 `AI 服务响应异常 (HTTP 401)`，`ChatPage.vue:599-600` 再统一转成用户看到的「AI 服务响应异常，请检查网络连接后重试。」——**这条文案掩盖了真实的 401**，是本次排查耗时的主要原因。

## 4. 与文档/代码的冲突（待修正项）

### 4.1 Milvus 已启用鉴权（2026-11-24 更正）

- **本文档初版此处结论「Milvus 无认证」是错的**，原因是最早只 grep 了 `authorizationEnable`（漏掉 d），未查 `milvus.yaml` 的 `security` 段。
- 实测事实：`deploy/milvus/milvus.yaml:938` 为 `authorizationEnabled: true`，`superUsers` 为空，`defaultRootPassword` 为 6 字符；`RAG-Knowledge-System/backend/.env` 配 `MILVUS_USER=root` + 同值 `MILVUS_PASSWORD`；匿名连接会报 `missing authorization in header`。
- 结论：鉴权**已生效**，但 8002 用的是 **root 超级账号**。**待核实**：专用业务账号（如 `milvus_rag`）是否真实建过——从 `.env` 现状看没有，专用账号属计划项。**不是本次故障成因**。

### 4.2 `application.yml` 注释与算法不一致

`backend-java/.../application.yml:53` 注释写「HS512 需要至少 512 位 = 64 字节」，实际 `JwtUtil` 用 `Keys.hmacShaKeyFor`（HS512 需 ≥64 字节）。当前 `JWT_SECRET` len=64，刚好满足；若将来换成更短的密钥会静默降级到其它 HS 算法，与 8002 pin 的 HS512 失配。列为风险。

### 4.3 前端错误文案掩盖 HTTP 状态

`ChatPage.vue:599-600` 把任何 error 统一成「请检查网络连接」。401/403/429 与真正的网络故障不可区分，排查成本高。建议后续在 toast 里保留 `HTTP <code>` 片段（本次未改，属前端体验优化项）。
