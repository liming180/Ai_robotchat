## 一、背景与问题

`/notes` 页面当前是**假功能**：

## 二、表结构

新建 `note` 表，字段口径对齐现有 `conversation` / `companion`：

```sql
CREATE TABLE IF NOT EXISTS note (
    id VARCHAR(36) PRIMARY KEY,
    user_id VARCHAR(36) NOT NULL,
    companion_id VARCHAR(36) NOT NULL,
    content TEXT NOT NULL,
    -- 逗号分隔，与 companion.tags 同一口径（P1-4：不展开为数组、不建标签表）
    tags VARCHAR(500),
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted TINYINT(1) NOT NULL DEFAULT 0,
    KEY idx_note_user_updated (user_id, updated_at),
    -- 复合索引：级联删除执行 WHERE companion_id=? AND deleted=0，两个条件都被覆盖，无需回表过滤
    KEY idx_note_companion_deleted (companion_id, deleted)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**索引理由**：

| 索引 | 支撑的查询 |
| --- | --- |
| `idx_note_user_updated (user_id, updated_at)` | 列表主查询：按 user 过滤 + 按更新时间倒序。复合索引让 `WHERE user_id=? ORDER BY updated_at DESC` 走索引即排序，避免 filesort |
| `idx_note_companion_deleted (companion_id, deleted)` | 删除伴侣时 `logicDeleteByCompanionId` 的 `WHERE companion_id=? AND deleted=0` 两个条件被索引完全覆盖，无需回表过滤；也支撑「某伴侣的笔记」筛选（本期不做 UI） |

**不建**：`tags` 上的索引（当前是 `LIKE` 前端过滤，不做服务端标签查询）、`deleted` 单列索引（已并入 `idx_note_companion_deleted` 复合索引，单列冗余）。

### 迁移方式

**沿用仓库现有双轨**（`schema.sql` 给新库、`migration.sql` 给老库）：

1. `backend-java/src/main/resources/schema.sql` — 追加上述 `CREATE TABLE IF NOT EXISTS note`
2. `backend-java/src/main/resources/migration.sql` — 追加同样语句 + 注释说明用途
3. 本机执行：`mysql -uroot -p ai_companion < backend-java/src/main/resources/migration.sql`
4. **不做 Flyway/Liquibase**：仓库现有 5 张表都是手写 SQL 双轨，引入迁移框架超出本期范围（与「范围收紧」一致）

## 三、4 个端点契约

统一前缀 `/api/v1/notes`，全部走现有 JWT 鉴权（`SecurityConfig` 未放行，天然受保护），响应统一 `Result<T>`：

```json
{ "code": 200, "message": "...", "data": ..., "timestamp": "2026-11-16T10:00:00" }
```

`userId` **一律从 `Authentication.getPrincipal()` 取**，不接受请求体传入——避免越权（对齐 `CompanionController` 口径）。

### 3.1 列表

```
GET /api/v1/notes?companionId=&keyword=&page=1&pageSize=50
```

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `companionId` | 否 | 不传 = 全部伴侣的笔记 |
| `keyword` | 否 | 对 `content` 做 `LIKE %kw%`；tags 不参与服务端搜索（前端已有本地标签过滤） |
| `page` / `pageSize` | 否 | 默认 1 / 50，`pageSize` 上限 100（对齐 8002 的 `le=100` 习惯） |

**响应**：

```json
{
  "code": 200,
  "message": "获取成功",
  "data": {
    "items": [
      { "id": "...", "companionId": "...", "content": "...", "tags": "温柔,治愈",
        "createdAt": "2026-11-16T10:00:00", "updatedAt": "2026-11-16T10:00:00" }
    ],
    "total": 12,
    "page": 1,
    "pageSize": 50
  }
}
```

> **与 `GET /conversations` 的差异说明**：会话列表返回**纯数组**（历史遗留，文档已标注），笔记是新端点，**返回分页对象**。不复制旧的不一致口径。

### 3.2 创建

```
POST /api/v1/notes
```

```json
// 请求（content 必填）
{ "companionId": "companion-uuid", "content": "今天聊到的事", "tags": "温柔,治愈" }
```

- `companionId` 必填，且必须是**当前用户可见的伴侣**（存在且 `deleted=0`；预置伴侣允许——用户可以对预置伴侣记笔记）
- `content` 必填，`@NotBlank`
- `tags` 可选，逗号分隔字符串，超 500 字符返回 400

**响应**：`data` 为单条 Note（结构同列表项）。

### 3.3 更新

```
PUT /api/v1/notes/{id}
```

```json
{ "content": "改后的内容", "tags": "温柔", "companionId": "可选，允许换归属" }
```

- 所有字段为 `null` 表示不修改（对齐 `PUT /companions/{id}` 的部分更新语义）
- 归属校验：笔记的 `user_id` 必须等于当前用户，否则 **404「笔记不存在」**

### 3.4 删除

```
DELETE /api/v1/notes/{id}
```

- 逻辑删除（`@TableLogic` 自动转 UPDATE）
- 归属校验同 3.3，他人笔记 **404**

### 错误码

| 场景 | HTTP | code | message |
| --- | --- | --- | --- |
| 成功 | 200 | 200 | 见各端点 |
| `content` 为空 / `tags` 超长 / 参数校验失败 | 400 | 400 | 校验注解的 message |
| 笔记不存在 | 400 | 400 | 「笔记不存在」 |
| 他人笔记（与「不存在」合并） | 400 | 400 | 「笔记不存在」 |
| `companionId` 无效 | 400 | 400 | 「伴侣不存在」 |
| 未带 token | 403 | — | Spring Security 拦截 |

> **为什么越权也用 400 而不是 404**：`GlobalExceptionHandler` 现有映射是 `IllegalArgumentException → 400`，全项目一致（伴侣删除越权也是 400「无权删除该伴侣」）。**但笔记刻意不区分「不存在」与「无权」**，文案统一「笔记不存在」——避免用状态码/文案探测他人笔记是否存在（对齐 Python 记忆接口的口径）。若后续要求严格 REST 语义，可再加 `NotFoundException → 404`，本期不引入新异常类型。

## 四、删除伴侣的级联（同删笔记）

**口径对齐**：与 `conversation` / `message` / `user_companion` 完全一致，在同一个 `transactionTemplate.executeWithoutResult` 事务内逻辑删除，不留孤儿笔记。

修改 `CompanionServiceImpl.deleteCompanion` 的事务块（当前 4 步 → 5 步）：

```java
transactionTemplate.executeWithoutResult(status -> {
    List<String> conversationIds = conversationMapper.selectIdsByCompanionId(companionId);
    if (!conversationIds.isEmpty()) {
        int msgRows = messageMapper.logicDeleteByConversationIds(conversationIds);
    }
    int convRows = conversationMapper.logicDeleteByCompanionId(companionId);
    int noteRows = noteMapper.logicDeleteByCompanionId(companionId);   // ← 新增
    int ucRows = userCompanionMapper.logicDeleteByCompanionId(companionId);
    companionMapper.deleteById(companionId);
});
```

新增 `NoteMapper.logicDeleteByCompanionId`：

```java
@Update("UPDATE note SET deleted = 1 WHERE companion_id = #{companionId} AND deleted = 0")
int logicDeleteByCompanionId(@Param("companionId") String companionId);
```

**顺序说明**：笔记放在 `conversation` 之后、`user_companion` 之前，与现有「子表先于主表」的次序一致；同事务内任何一步抛异常整体回滚。

**8002 失败时**：仍在事务外 fail-fast（502 + MySQL 不动），笔记自然也不会被删——与现有行为一致。

## 五、前端改造点

### 5.1 `stores/note.ts`：localStorage → 后端 API

完全重写，对齐 `stores/memory.ts` 的既有范式（它已成功从 localStorage 迁到 Python）：

| 旧（localStorage） | 新（Java API） |
| --- | --- |
| `notes` ref 数组 + `loadFromLocalStorage()` | `loadNotes(params)` → `javaFetch('/api/v1/notes?...')` |
| `addNote(...)` 本地 push | `await javaFetch('/api/v1/notes', { method:'POST', body })`，成功后 `unshift` |
| `updateNote(...)` 本地改 | `PUT /api/v1/notes/{id}`，成功后替换数组项 |
| `deleteNote(...)` 本地过滤 | `DELETE /api/v1/notes/{id}`，成功后过滤 |
| `saveToLocalStorage()` | **删除**（不再有本地持久化） |

**保留的纯前端能力**（不涉及后端）：

- `allTags` computed：从 `notes` 的 `tags` 数组聚合（数据来源换成 API 返回值）
- `filterByTag(tag)` / `searchNotes(query)`：本地过滤（列表已在内存，避免每次输入都打后端）

**DTO 转换**：后端 `tags` 是逗号分隔字符串，前端 `Note.tags` 是 `string[]`，需在 `toNote(dto)` / `toPayload(note)` 处转换——复用 `stores/companion.ts` 的 `tags` 处理方式。

**错误处理**：加载失败时 `error` 置消息（不再有「离线缓存兜底」，因为没有本地副本了——`clearBusinessCache()` 里的 `ai-notes` key 相应从常量列表中移除，见 5.4）。

#### 旧 localStorage 笔记数据的处置（**明确：不迁移，废弃**）

`ai-notes` key 里可能存有用户此前在浏览器本地写的笔记。切换后端后：

- **不做一次性迁移**：不读取 `ai-notes`、不上传旧数据、不提示用户。
- **旧数据遗留**：`ai-notes` 不会被自动删除（`clearBusinessCache()` 仍会在后续清理时移除它，但不会主动读）。用户可以在浏览器 DevTools 里自行找回，但产品层面视为已废弃。
- **为什么不做迁移**：① 旧数据结构简陋（无 `updatedAt`、`companionId` 可能是失效 ID）；② 迁移需「读本地 → 逐条 POST」，存在部分失败、重复提交等一致性问题；③ 该功能此前**从未有新增入口**（`addNote` 零调用），`ai-notes` 里实际上极可能**一条数据都没有**，迁移是零收益的复杂度。
- **记录位置**：本方案 + `docs/前端技术文档.md` 的 store 表格备注，避免后人以为「笔记数据丢了」是 bug。

> 若后续确实出现用户投诉旧笔记丢失，再按「一次性导入脚本」补做，需先确认 `ai-notes` 里是否真有数据（用 grep/DevTools 核实），不预先开发。

## 六、越权与预置语义

| 场景 | 行为 | 理由 |
| --- | --- | --- |
| 读他人笔记 | 列表按 `user_id` 过滤，**查不到**（无法通过列表探测） | 列表天然隔离 |
| 改/删他人笔记 | **400「笔记不存在」**（与真不存在同一文案） | 不复用「无权」文案，避免探测 |
| 给预置伴侣记笔记 | **允许** | 预置伴侣只是不可编辑/删除，用户仍可与它聊天，笔记属于用户自己的内容 |
| 给不存在的伴侣记笔记 | 400「伴侣不存在」 | 创建时校验 |
| 伴侣已被逻辑删除后再记笔记 | 400「伴侣不存在」 | 校验时过滤 `deleted=0` |
| 删除他人创建的伴侣 | 走现有 400「无权删除该伴侣」，**不触发笔记级联** | 校验在级联之前 |

## 八、明确不做（范围收紧）

| 不做 | 理由 |
| --- | --- |
| 笔记分享 / 协作 | 产品当前无社交属性，且需权限模型重构 |
| Markdown 渲染 | 纯文本足够覆盖「记录想法」场景，渲染会引入 XSS 面与依赖 |
| 笔记富文本编辑器 | 同上，且显著增加前端复杂度 |
| 笔记附件 / 图片 | 需接 uploads 与清理机制，与 T-3 耦合，本期不碰 |
| 笔记服务端标签查询 | 列表已在内存，前端本地过滤即可；标签表会打破 P1-4 契约 |
| 笔记分页 UI | 后端支持分页参数，前端一期先一次拉 50 条；超过再补 |
| 引入 Flyway/Liquibase | 与现有手写 SQL 双轨不一致，超范围 |
| 笔记离线缓存 | 刻意不做——假持久化正是本次要消灭的问题 |
| 旧 `ai-notes` 数据迁移 | 该功能从未有新增入口（`addNote` 零调用），本地极可能无数据；迁移为零收益的高复杂度，明确废弃 |
