# 功能开发需求文档：前后端打通与接后端落地

## Plan Header

**Goal**：把前端从 localStorage mock 切换到 Java Spring Boot(8080) 真实 API，聊天流式回复完成后落库，清理全部假数据与残留组件，使四服务架构（前端 3000 / Java 8080 / Python AI 5000 / RAG 8002）按设计意图真实联通，达到可上线验收标准。

**Architecture**：

```
frontend(3000)
  ├─ src/lib/api.ts ──────────HTTP JSON──▶ Java(8080) REST + JWT
  │     auth / users / companions / chat(conversations·messages落库)
  ├─ useStreamingChat.ts ────SSE────────▶ Python(5000) 流式聊天+建议
  │     (环境变量取地址；流结束后回写 Java 落库)
  └─ CreatePage.vue ─────────HTTP───────▶ Java(8080) POST /ai/generate-avatar
                                              └─代理─▶ Python(5000) /api/v1/ai/generate-avatar
Python(5000) search_knowledge ──HTTP────▶ RAG(8002) /api/v1/kb/retrieve（内建 RAG 降级兜底）
```

**Tech Stack**：Vue 3 + TS + Pinia + Tailwind（前端）；Java 21 + Spring Boot 3 + Spring Security JWT + MyBatis Plus + MySQL + Redis（业务后端）；FastAPI + LangChain 1.x + OpenAI 兼容双模型（AI 服务）；fetch + ReadableStream（无 Axios/WebSocket）。

**范围外（明确不做）**：WebSocket 聊天、Java/Python 响应格式统一、Python 端完整 JWT 验签（仅加共享密钥头）、Element Plus 引入、新功能页面、记忆/情绪表迁到 MySQL（短期留 Python）。

**2026-11-12 修订说明**：本版新增**任务零**（后端能力补齐）与**任务九**（四服务联调验收），并修订任务三/四/五。原因是复核代码后确认两个架构级缺口（收敛点 P0-6、P0-7）：记忆/情绪在 Java 侧无表无接口、头像与聊天图片无存储能力。不补这两块，任务四/五写完仍跑不通。

### 实施中发现的 3 个坑（已修正，后续别踩）

1. **`/uploads/**` 被 Spring Security 拦截**：`anyRequest().authenticated()` 会把静态图片也挡住，而 `<img>` 无法带 Authorization 头 → 浏览器 403。必须在 `SecurityConfig` 显式放行，安全性靠 URL 中随机 UUID 文件名（不可枚举）。
2. **`addResourceHandlers` 必须用绝对路径的 `file:` URI**：直接传 `./uploads` 会被按 classpath 解析，导致上传成功但访问 404。用 `Paths.get(dir).toAbsolutePath().normalize().toUri().toString()`。
3. **`schema.sql` 的 `INSERT` 需幂等**：原为裸 `INSERT`，重复执行报 1062。改 `INSERT IGNORE`。（`CREATE TABLE IF NOT EXISTS` 本身幂等，但 `ALTER` 需单独走 `migration.sql`。）

### 环境相关决策（不写死进代码）

- **8080 已被无关项目占用**（`Xiaoyi_RAG_bookstore` 的 jar）。验收统一用 `--server.port=8081 --app.upload.base-url=http://localhost:8081` 临时启动，不干扰现有服务；`application.yml` 的 `server.port` 保持 8080 不变。
- **本地 Redis 未启动**，因此 mock 模式的验证码存储刻意做成进程内 Map，保证不依赖 Redis 也能跑通注册链路。

### 实现口径（与计划的差异，均已按代码实际情况定稿）

1. **401 与 403 都触发刷新**：Java 未配 `AuthenticationEntryPoint`，`anyRequest().authenticated()` 对未登录请求返回 **403** 而非 401（任务零验收记录中「无 token 403」已印证）。`javaFetch` 对 `res.status === 401 || 403` 统一按鉴权失败处理：先调 `/api/v1/auth/refresh`，成功则重试一次，失败则清 token + 清 `ai_companion_user` 缓存并跳 `/login`。未来 Java 补 EntryPoint 返回 401 时无需改前端。
2. **`CreatePage.vue` 走 `aiFetch` 而非 `javaFetch`**：任务五（Java 头像代理）未完成，`AIServiceImpl.generateAvatar` 仍直接返回 dicebear URL。按计划自带的兜底条款临时直连 Python；任务五完成后改一行即可。
3. **不 import Pinia store / router（静态）**：`api.ts` 只读写 localStorage，跳转登录用动态 `import('@/router')`，避免 `api → router → pages → stores → api` 循环依赖。token 键名 `ai_companion_access_token` / `ai_companion_refresh_token`，任务三的 user store 直接复用 `TOKEN_KEYS`。
4. **环境变量缺失时报可读错误，不静默回落 localhost**：`readEnv()` 抛 `ApiError`，否则会破坏「`grep -r "localhost:" frontend/src` = 0」红线。
5. **`.gitignore` 的 `lib/` 规则误伤前端源码（实施中发现，重要）**：第 39 行 `lib/`（Python 模板规则）把整个 `frontend/src/lib/` 目录忽略了——`avatar.ts`、`utils.ts` 此前**从未进入 git**，全新 clone 后 `CreatePage.vue` 的 import 会直接失败。已加 `!frontend/src/lib/` 例外，三个文件变为未跟踪待提交。
6. **`.env.development` 也被 `*.env.*` 规则忽略**：已加 `!frontend/.env.development` 例外（仅 localhost 地址、无密钥，本就应入库）。

### 实现口径（与计划的差异）

1. **`isAuthenticated` 以 access token 为准，而不是 `user` 对象**。原 store 用 `user !== null`；清 token 但残留用户缓存时会出现"有用户无 token"的假在线态。现在 token 是唯一事实源，`user` 仅作展示缓存。
2. **`api.ts` 里加了 `accessToken` 响应式 ref**：localStorage 本身不响应式，`isAuthenticated` 若直接读 localStorage，登出后 LoginPage 的 `watch(isAuthenticated)` 不会触发、Navbar 也不会切换。`setTokens/clearTokens` 同步更新该 ref，`getAccessToken()` 返回值不变，守卫与 `javaFetch` 无需改。
3. **`user store` 不再用 `onMounted` 恢复缓存**：`defineStore` 的 setup 函数不在组件上下文，`onMounted` 永远不会执行（原代码是死逻辑）。改为模块级 `loadCachedUser()` 在 store 创建时同步读 localStorage。
4. **新增 `fetchMe()`**：有 token 无用户缓存（如清站点数据后仍保留 token、或换标签页）时补齐用户信息。任务三页面暂未强制调用，为任务四读取 `userId` 留的兜底。
5. **login/register 请求体走 `auth: false`**：登录注册本就无 token，且若走默认鉴权，token 过期时会触发刷新逻辑造成无意义往返。
6. **`goAfterLogin()` 只接受以 `/` 开头的 redirect**，防开放重定向；`/login` 自身不递归。

### 实施中发现的坑（务必留档，任务九还会再遇到）

#### 坑 1（计划外，已修）：Spring Security 未开启 CORS，浏览器所有需鉴权请求 403

**现象**：前端 `npm run dev` 起来后，登录成功、token 已写入，但 `/square` 报
`伴侣列表加载失败：无法连接服务 http://localhost:8082（Failed to fetch）`。
curl 直连同一接口带 token 是 200，**只有浏览器失败**。

**根因**（curl 复现确认）：
- `WebConfig.addCorsMappings(...)` 只配在 **MVC 层**；
- `SecurityConfig.securityFilterChain` **没有 `.cors(...)`**。Spring Security 6 的过滤器链执行在 MVC **之前**，浏览器发出的预检 `OPTIONS` 请求**不带 `Authorization` 头**，被 `anyRequest().authenticated()` 判成未认证 → **403** → 浏览器判定 CORS 失败 → 后续真实请求压根没发。

复现命令与结果（修复前）：
```bash
# 不带 Authorization（浏览器真实行为）→ 403
curl -i -X OPTIONS http://localhost:8081/api/v1/companions \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: authorization"
# 手动补上 Authorization → 200（这就是为什么 curl 测不出来）
```

**修复**：`SecurityConfig` 加
```java
.cors(Customizer.withDefaults())
```
未指定 `CorsConfigurationSource` 时自动回落到 `WebConfig` 已有的白名单，无需重复配置。

**为什么任务三没暴露**：任务三浏览器只调了两类接口——`/api/v1/auth/**`（`permitAll()`，预检不拦）和 Python 5000（FastAPI 自带 CORS 中间件）。**任务四是第一次从浏览器调用需鉴权的 Java 接口**，因此第一次踩到。`curl` 测接口永远测不出这个坑，必须用真实浏览器。

**任务九注意**：四服务联调时只要换了前端端口（3000→其他），只要 Security 开了 `.cors()` 就仍复用 `WebConfig` 的 `allowedOriginPatterns("*")`；**若以后收紧白名单，务必要同步改 `WebConfig`，而不是只加 `.cors()`**。

#### 坑 2：旧编译产物会静默"验证失败"

`8081` 上的 Java 进程是任务三时期启动的，class 文件不含 `generate=false` 逻辑；`5000` 上的 Python 进程仍在返回 `_get_sample_memories` 的假数据。
第一次验收时表现为"`generate=false` 不生效、B 账号也能查到 5 条假记忆"——**不是代码问题，是进程陈旧**。
**教训**：改完后端代码必须重启进程再验收；并行保留旧实例时，验收报告要写明"新代码以哪个端口为准"。

#### 坑 3：Playwright 断言踩到的两个假象

1. **`article` 元素数量对不上**：广场页"我的收藏"区和"全部伴侣"区都用 `<article>`，收藏后总数变 5，误判"加载了 5 个伴侣"。应限定 `page.locator(".companion-grid article")`。
2. **流式未结束就发下一条 → 消息被丢弃**：`ChatPage.sendMessage` 开头有 `if (isTyping.value) return`。E2E 用固定 `wait_for_timeout` 等待，AI 回复慢时下一条直接被吞，落库只剩一条。改为轮询等待 `.animate-bounce` 与 `.animate-blink` 都消失后再发送。

#### 坑 4：本机 Playwright 未装浏览器

`playwright install` 未执行过，`p.chromium.launch()` 报 `Executable doesn't exist`。
改用本机已装 Chrome：`p.chromium.launch(channel="chrome")`，免下载。

### 实施中新发现的坑

#### 坑 5（重要）：历史消息里的本机图片 URL 会让整条请求 400

- **现象**：浏览器里带图发言，AI 回复预设文案；后端日志 `Zhipu AI stream error: Error code: 400 - 图片输入格式/解析错误`。但用 curl 直连同一接口、同样 base64 图片却正常。
- **根因**：前端把历史消息的 `images`（落库的是 `http://localhost:8082/uploads/xxx.jpg`）一并传给 Python，`_build_messages()` 原样转成 `image_url` 发给智谱。**云端模型无法访问开发机的 localhost 地址** → 400 → 整条链降级到 `PRESET_RESPONSES`。
- **修复**：`_build_messages()` 只回传 `data:` 开头的图片；历史中的 URL 图片直接跳过，并追加一条 system 说明「历史图片未随上下文传输，不要声称用户没发图」。
- **注意**：**占位文字不能塞进历史消息的 content**。第一版实现往 content 拼了「此消息曾附带图片」，结果模型把它理解成"用户说过图片没传过来"，转而忽略当前轮真正附带的图片。必须用独立 system 消息。
- **教训**：`curl` 测接口测不出这类问题，必须用真实浏览器跑完整历史上下文。

#### 坑 6：Windows 僵尸 TCP socket 导致「改了代码不生效」

- **现象**：改了 `main.py`、重启 Python，但请求表现和改前完全一致（同样的 400、同样的预设文案）。
- **根因**：`taskkill` 后进程已死，但 `netstat` 里该端口的 LISTENING 条目仍绑定旧 PID（Windows TCP 未回收）。新进程在**同一端口**启动时，请求被这个僵尸 socket 接走，根本没到新进程。
- **排查方法**：`netstat -ano | grep :端口` 出现**同一端口两行、两个不同 PID** 即为征兆；`tasklist //FI "PID eq <死PID>"` 会提示"没有运行的任务"。
- **解法**：换一个全新端口启动（本次 5001→5002→5003→5010），或等待 TCP 超时回收。
- **注意**：`python main.py` 会带 uvicorn `--reload`（WatchFiles reloader），进程树有 reloader + worker 两层，`taskkill` 只杀一层会留下孤儿。

### 头像不出图排查与修复（2026-11-13）

#### 现象

用户在浏览器（前端 3000）点「AI 生成专属头像」后，预览区仍是文字占位 SVG（绿色渐变 + "温柔"字样），未出真实图。但 5020 实例上 CogView 实测是通的。

**第 2 条：浏览器抓包（3001 → 5010）**

STATUS: 200
BODY:   {"success":true,"message":"Avatar generated successfully",

### 与计划的差异（均为实施中实测发现，必须留档）

1. **AI 头像必须落盘，不能纯透传**。计划说 AI 头像返回的是远程 URL、不必经 uploads——但 CogView 返回的是 `maas-watermark-prod-*.ufileos.com` 上的**第三方临时直链**（`backend/app/ai/avatar_store.py` 的注释也写明 *temporary, may have watermark*）。而 `companion.avatar` 是持久化字段，存直链等于给历史伴侣埋一个会过期的裂图。改为：Java 拿到直链后立即下载 → `FileService.saveImage()` → 返回本站 `/uploads/...`。
2. **端口是 8081 不是 8080**（8080 被无关项目 `xiaoyi-rag-server` 长期占用）。
3. **降级字段从 1 个变 4 个**。计划只要求 `data.avatarUrl`；11-13 给 Python 加了 `fallback` / `fallbackReason` / `model`。Java 必须透传，否则前端那条黄色降级提示条失效，退回静默降级。
4. **Java 自身兜底也要标降级**。计划让 Java 异常时"降级 dicebear"就完事——这样前端拿到一个正常 URL 会当成功。实现为 `fallback=true` + `fallbackReason`（如「代理调用失败: ResourceAccessException」）。

### 实施中新发现的两个计划外缺陷（+1 个预防项）

**缺陷 1：预设头像必然创建失败**。`CreatePage` 的 5 个预设头像、以及 AI 失败时的本地兜底，都是 `data:image/svg+xml;base64,...`。而上传白名单（`FileServiceImpl.ALLOWED_TYPES`）只有 jpg/png/webp/gif，**不含 svg**。实测：`POST /api/v1/uploads` 传 SVG → `400 不支持的图片类型：image/svg+xml`。即「不点 AI 生成、直接用默认头像」这条路 100% 失败。任务四验收没暴露是因为当时只测了用户上传 JPEG。
修复：前端新增 `toJpegDataUrl()`，入库前把 SVG 光栅化成 JPEG。

**缺陷 2：透明头像变黑底**。`canvas.toBlob('image/jpeg')` 不保留 alpha，透明区域渲染为黑色。修复：绘制前 `fillStyle='#ffffff'` + `fillRect` 垫底。实测落盘 JPEG 原透明区像素为 `(255,255,255)`。

**缺陷 3（预防，未实际发生）：dicebear seed 直接拼中文人设会撑爆字段**。中文 URL 编码后每字约膨胀 9 倍（`%E6%B8%A9%E6%9F%94...`），长人设拼进去会把 URL 顶到 500 字符以上，**降级路径自己崩溃**。改为「人设 SHA-256 前 8 位 + 时间戳」，实测降级 URL 仅 71 字符。
