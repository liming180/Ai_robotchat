## 一、缺陷定义

| 项 | 值 |
| --- | --- |
| 问题原文 | `这个项目用的技术栈是什么来着？`（`logs/trigger_experiment_v6.py:51`，kind=`edge`） |
| 期望文档 | `tests/rag_regression/fixtures/a/08-preferences.md` |
| 期望内容 | 第 4 行「示例项目：使用 FastAPI 和 PostgreSQL，不替换成 Flask 或 MySQL。」 |
| 历史成绩 | v3 1/3、v6 1/3——**答案级全有或全无**，不是部分内容丢失 |

「1/3」口径：3 轮里 1 轮召回整块并答对，2 轮检索未召回、模型按规则 7 报「知识库里没有找到」。

## 二、根因（带复现证据）

三层叠加，主因是**块内稀释**：

1. **块内稀释（主因）**：08-preferences 整篇 202 字 < `chunk_size=500`，6 个无关 bullet 被压成 1 块，期望内容只占 ~19%。embedding-3 实测余弦：整块 vs 原话 **0.3975**，单条「示例项目」bullet vs 原话 **0.4711**，相差 0.07~0.08。
2. **top-k 拥挤（次因）**：09-programming-guide 有 14 块（collection a 共 22 块，占 64%）。topK=4 时 08 排**第 5**（0.3977），第 4 名 01-python-env 0.3990，差 **0.0013**。
3. **Agent 改写 query 的随机性（触发器）**：日志解出 54 条真实工具调用、12 个 E-2 变体，只有带「框架 / 数据库」字面时才进 top-4；只写「技术栈 / 技术偏好」时排第 6~8。12 变体 4 命中 ≈ 1/3，与历史成绩吻合。

排除项：**阈值不是原因**（`RETRIEVE_SCORE_THRESHOLD=0.0`，0.3977 不被过滤）；hybrid/BM25 救不了（全库 grep「技术栈」0 命中，字面匹配无锚点）。

链路旁证：`text_parser.py` 把 H1 收进 `title` 后不进入正文（`text_parser.py:47`），`ingest.py:153` 只嵌入 `content`，标题不参与向量；08 的 H1「使用偏好」不含「技术栈」，因此标题注入对 E-2 无效。

## 三、实施方案

### 方案 A：topK 4 → 8，并抽成配置

| 文件 | 改动 |
| --- | --- |
| `backend/app/ai/config.py` | 新增 `RAG_TOP_K: int = 8`，`__post_init__` 支持 `RAG_TOP_K` env 覆盖 |
| `backend/app/ai/langchain_client.py` | `topK` 由硬编码 `4` 改为 `int(getattr(config, "RAG_TOP_K", 8) or 8)` |
| `RAG-Knowledge-System/backend/app/core/config.py` | `retrieve_top_k` 默认 4 → 8 |
| `RAG-Knowledge-System/backend/tests/rag_regression/run_regression.py` | `verify_retrieve(..., top_k=8)` + `--top-k` 参数，不再硬编码 4 |
| `backend/.env.example` | 补 `RAG_TOP_K=8` 说明 |

依据：E-2 观测到的最远排名是第 8，topK=8 覆盖全部变体。dense-only 下无 rerank 调用，不存在 Milvus v2.6.0 那个源码硬编码 30s rerank deadline 的问题（该限制只在 `RERANK_ENABLED=true` 时生效）。

### 方案 B：正文含多个列表项时按列表项切块

| 文件 | 改动 |
| --- | --- |
| `RAG-Knowledge-System/backend/app/workers/ingest.py` | 新增 `_LIST_ITEM_RE`、`_split_list_items(content)`；`_chunk()` 先按列表项拆段，再对每段做原有 `RecursiveCharacterTextSplitter` |

规则：`- / * / + / 1. / 1)` 开头视为列表项；**只有 ≥2 个列表项时生效**，单个或零个列表项与改动前逐字节一致。每个片段从列表项所在行起、含其后续行；列表项之前的前言单独成段。返回片段仍交给原有 splitter，长段不会被无限放大。

对 fixture 的实际影响：`a/08-preferences.md` 1 块 → **6 块**（26/50/31/32/29/29 字），`b/08-preferences.md` 1 块 → **6 块**。其余 17 篇 fixture（0 个列表项）切块结果不变，`09-programming-guide` 仍为 14 块。

重灌方式：`POST /api/v1/kb/documents/{doc_id}/reindex`（8002 自带路由，`reset_for_reindex` 先删 MySQL 切片与 Milvus 向量，再走完整解析→切片→向量化）。**只重灌两篇 08**，其余 17 篇未动。回滚：把 `_split_list_items` 去掉后对同一 doc_id 再 reindex 一次即可回到单块，内容源文件未改。

2. **短块噪声（线上会真实生效）**：bullet 切块把 08 摊成 6 条 25~50 字短块，隔离/否定用例的 top1 从「无关文档噪声」变成「08 的无关 bullet」（0.2845/0.3420/0.3669/0.3043）。**这些分数低于的是回归脚本的 0.5 断言阈值，不是线上阈值**——线上 `RETRIEVE_SCORE_THRESHOLD=0.0` 不过滤，这些块会实际进入 topK=8 的上下文。影响是「多几条无关短句」，不是答错；但后续若引入 rerank 或设置线上阈值，这批短块需重新评估（阈值过高会连带压掉其他短文档的正例）。
3. **只重灌了 08两篇**：其余 17 篇 fixture 不含列表项，切块结果不变，但若将来新增含列表项的文档，会走新逻辑，需要在导入后复核块数。

5. **A-CONTRAST-02 仍 FAIL**：既有缺陷（top1 为 09 而非 03-sql-index），与本批无因果关系，未处理。
6. **切块规则的适用范围**：围栏/嵌套/水平线/年份句点已在审计后修正并有单测锁定，但「一个列表项内含多段正文」仍整体成块（符合预期）；含表格、引用块、HTML 块的文档不在本批覆盖范围。
