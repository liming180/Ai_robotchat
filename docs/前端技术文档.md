## 三、当前网络调用（关键事实，2026-11-15）

**前端已接 Java 8081**，业务数据全部走后端（任务三/四/五完成）。

三条出站链路：

| 入口 | 目标 | 端点 | 用途 |
|------|------|------|------|
| `lib/api.ts` `javaFetch` | Java 8081 | `/api/v1/**`（auth/companions/chat/memory 由 store 调） | 业务与鉴权 |
| `composables/useStreamingChat.ts` | Python 5000 | `POST /api/v1/ai/chat/stream` 或 `/chat/langchain/stream`（enableRAG 切换） | SSE 流式聊天 |
| `lib/api.ts` `aiFetch` | Python 5000 | `/api/v1/memory/*`、`/api/v1/mood/*` | 记忆/情绪读写 |

- 所有地址走 `.env.development` 的 `VITE_API_BASE_URL`（8081）/ `VITE_AI_BASE_URL`（5000），**源码零硬编码**。
- SSE 请求头注入 `X-Service-Token`（`VITE_SERVICE_TOKEN`），与 Python 的 `SERVICE_TOKEN` 对齐；未配置则不发送该头。
- 流式结束后 `chatStore.saveMessages()` 用 `generate=false` 把 user+assistant 两条落库到 Java。

## 四、SSE 流式聊天（useStreamingChat）

- 协议：`fetch` POST + 逐行解析 `data: {...}`（非 EventSource，因需传 body）
- 帧格式：`{"delta": "增量文本", "done": false}`；结束帧 `{"delta": "", "done": true}`
- 三层降级由后端负责（LangChain → SDK 直连 → 预设库），前端只消费 delta
- LangChain 通道为**模拟流式**（全量生成后切块），前端感知为块状到达

```ts
// 现状核心片段（简化，2026-11-15）
const headers = { 'Content-Type': 'application/json' }
if (import.meta.env.VITE_SERVICE_TOKEN) headers['X-Service-Token'] = import.meta.env.VITE_SERVICE_TOKEN
const payload = {
  userMessage, systemPrompt, messages, images,
  userId,                     // 登录态真实 UUID（P0-3 已完成）
  companionId,                // RAG 知识库路由（任务七）
}
```

| Store | 职责 | 数据源现状（2026-11-15） |
|-------|------|-----------|
| user | 登录态、用户信息 | Java 8081 `/api/v1/auth/*`（任务三已接） |
| companion | 伴侣列表/当前伴侣 | Java 8081 `/api/v1/companions`（任务四已接） |
| chat | 对话与消息列表 | Java 8081 `/api/v1/chat/conversations`；流式走 useStreamingChat；localStorage 仅作只读缓存 |
| memory / emotion | 记忆、情绪 | Python 5000 `/api/v1/memory/*`、`/api/v1/mood/*`（任务四已接） |
| note | 用户笔记 | **Java 8081 `/api/v1/notes`（2026-11-16 任务十一已接）**：列表/新增/编辑/删除全走后端，本地不再有副本 |
| content | 收藏内容 | 仍为 localStorage（未接后端，本期不动） |

> **旧 `ai-notes` 本地数据不迁移**：切后端前该 key 里的笔记数据**直接废弃**。理由——历史版本**从未有新增入口**（`addNote` 零调用），本地极可能一条数据都没有；迁移需「读本地→逐条 POST」，有部分失败/重复提交等一致性问题，属零收益复杂度。`BUSINESS_CACHE_KEYS` 中的 `ai-notes` 已移除。若后续真有用户投诉旧笔记丢失，再补一次性导入脚本（先核实是否真有数据）。

### 业务缓存的清理口径（2026-11-16 第一批修复）

`lib/api.ts` 导出 `BUSINESS_CACHE_KEYS` 与 `clearBusinessCache()`，统一管理 7 个业务缓存 key：
`ai_companion_chats`、`ai_companion_catalog`、`ai-emotion-records`、`ai-memories`、`ai-saved-content`、`ai-shared-todos`、`ai-scene-settings`。

> `ai-notes` 已于 2026-11-16 移除（笔记改存后端，本地不再有副本）。

三个调用点：

| 调用点 | 行为 |
| --- | --- |
| `userStore.logout()` | 清 token + user 缓存 + **业务缓存** |
| `lib/api.ts forceLogout()`（401 被动登出） | 同上 |
| 个人页「清除本地缓存」 | **只清业务缓存**，保留 token 与 `theme`，用户保持登录 |

**为什么必须清**：业务缓存是服务器数据的本地副本，换账号后若后端请求失败走离线兜底，会把上一个账号的会话/情绪/记忆展示给新用户。`theme` 是纯界面偏好，不在此列。

> 历史坑：个人页原按钮叫「清除所有数据」，文案宣称删除对话和伴侣，实际只执行 `localStorage.clear()` + 刷新——后端一条没删却把人踢下线，属误导性假功能。2026-11-16 全站自测发现并修复。

## 九、2026-11-16 前端体验修复（8 项）

产品页自测发现的一批零散前端问题，全部只改前端、不涉及接口约定：

| 项 | 文件 | 修法 |
|----|------|------|
| 404 兜底 | `router/index.ts` + 新建 `pages/NotFoundPage.vue` | 路由表末尾加 `/:pathMatch(.*)*`；404 页沿用暗色渐变风格，提供「返回首页」按钮。**catch-all 必须放末尾**，否则会吞掉后面的路由 |
| 导航死链接 | `components/Navbar.vue` | 删除桌面端与移动端各一处 `href="#pricing"` 的「价格方案」——首页不存在 `#pricing` 区块 |
| 「了解更多」无行为 | `pages/HomePage.vue` | 新增 `scrollToFeatures()`，绑定 `@click`，`scrollIntoView({ behavior: 'smooth' })` 滚到 `#features` |
| ⌘K 假快捷键 | `pages/SquarePage.vue` | 搜索框加 `ref="searchInput"`；`onMounted` 挂 window keydown（`ctrlKey || metaKey` 且 `key === 'k'`）→ `preventDefault()` + focus，`onUnmounted` 移除。**焦点在其它输入控件内时不抢焦点**（见下方守卫说明） |
| 笔记「来自」下拉同名混淆 | `pages/NotesPage.vue` | option 文案改「名字 · 描述前缀」（超 12 字加 `…`，描述为空只显示名字）；select 关闭态补 `text-gray-800` 提升对比度。原生下拉展开层样式由浏览器控制，不改 |
| 情绪统计卡 0 → 真实值闪变 | `pages/EmotionCalendar.vue` | 页面内 `loading` ref，`onMounted` 包 `try/finally`（成功失败都置 false）；loading 时三个统计值一律显示「—」 |
| 历史页空态先闪 | `pages/HistoryPage.vue` | 同上加页面内 `loading`；loading 中显示「加载中…」，仅 `loading=false && 列表空` 才渲染「暂无聊天记录」 |

**为什么用页面内 `loading` 而不直接取 store 的 `loading`**：`chatStore.loadConversations` 等在未登录等分支会提前 `return`，store 的 loading 覆盖不到「本次 await 全流程结束」这个语义；页面内 ref 包 `try/finally` 才能保证「请求开始 true、成功失败都 false」。

**⌘K 守卫（2026-11-16 补测后新增）**：初版只做 `preventDefault + focus`，实测发现焦点在广场页「删除伴侣」确认模态的 `.modal-input` 内按 Ctrl+K，焦点会被抢到背后的搜索框——该输入框要求**精确输入伴侣名**才能点「确认删除」，被打断是可用性问题。现加守卫：`document.activeElement` 为 INPUT / TEXTAREA / contentEditable 且不是搜索框本身时，仅 `preventDefault()` 不抢焦点（仍阻止浏览器聚焦地址栏）。已实测：普通场景与 ⌘K 均可聚焦、搜索框内按键内容不丢、模态内不被打断、关闭模态后恢复。

**真实链路交叉验证（2026-11-16）**：mock 验收只覆盖渲染逻辑，另用真实接口补测——经 `/api/v1/auth/send-email-code`（本地 `app.email.mock: true`，验证码固定 123456）+ 注册建临时账号，UI 登录后创建同名「小智」自建伴侣、真实会话与心情记录：

- P1-5：下拉 5 项，两个「小智」分别显示「小智 · 温柔体贴的聊天伙伴，总是…」「小智 · 博学多才的知识助手，帮你…」，可区分；select 关闭态 `rgb(31, 41, 55)`。
- P1-6：真实接口 100ms 内返回，加载窗口极短；用「真实响应 + 2.5s 延迟」观测到三卡先「—」再变「3 / 快乐 / 2」，无 0 中间态。UI 录入带备注心情 → 刷新后备注仍在（`note` 字段落库，前端 store 传的正是 `note`）。
- P1-7：0~2400ms 显示「加载中」，3000ms 转列表并显示真实会话标题与消息预览，全程无空态闪现。
- 测试账号与全部业务数据已删除（MySQL `user`/`companion`/`conversation`/`message`/`note`/`user_companion` 按 `created_by`/`user_id` 精确清理，SQLite `user_moods` 同步清理），复测登录返回「邮箱或密码错误」，残留行数均为 0。
