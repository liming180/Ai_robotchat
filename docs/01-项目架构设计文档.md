## 🏗️ 一、四服务架构

### 1.1 架构理念

- **职责清晰**：前端只做 UI；Java 管业务与鉴权；Python 管 AI；RAG 服务管知识库
- **标准协议**：RESTful JSON + SSE 流式（不使用 WebSocket）
- **双 AI 通道**：文本走小米 MiMo，视觉（头像生成）走 GPTCODEX 中转站，均为 OpenAI 兼容协议

### 1.2 服务一览

| 服务 | 技术栈 | 端口 | 职责 |
|------|--------|------|------|
| 前端 frontend/ | Vue 3 + TS + Vite + Tailwind + Pinia | 3000 | UI、路由、状态 |
| 业务后端 backend-java/ | Java 21 + Spring Boot 3.3 + MyBatis Plus | 8080 | 用户/伴侣/对话落库、JWT 鉴权 |
| AI 服务 backend/ | Python 3.11 + FastAPI + LangChain 1.x | 5000 | LLM 对话、SSE 流式、头像生成、记忆/情绪 |
| 知识库 RAG-Knowledge-System/ | Python + FastAPI | 8002 | 文档上传、向量检索 |

### 1.3 架构图

```
┌────────────────────────────────────────────────────────────┐
│                      Web 浏览器 (Vue 3, :3000)              │
│                                                            │
│  lib/api.ts (javaFetch)  ─── JWT + JSON ──┐                 │
│  useStreamingChat (SSE)  ─── 流式直连 ─────┼──┐              │
│  lib/api.ts (aiFetch)    ─── 记忆/情绪 ────┼──┼──┐           │
└───────────────────────────────────────────┼──┼──┼───────────┘
                                            │  │  │
        ┌───────────────────────────────────┘  │  │
        ▼                                      ▼  ▼
┌──────────────────────────┐      ┌───────────────────────────┐
│ Java Spring Boot (:8080) │      │ Python FastAPI (:5000)    │
│ JWT 双 Token             │      │ LangChain create_agent    │
│ 用户/伴侣/对话/消息       │───▶  │ MiMo 文本 / GPTCODEX 视觉 │
│ 图片上传 /uploads        │      │ 记忆+情绪工具（SQLite）   │
│ MySQL 5 表 + Redis       │      │ SQLite + Chroma + SSE     │
└──────────────────────────┘      └──────────────┬────────────┘
                                                 │ search_knowledge
                                    ┌────────────▼──────────────┐
                                    │  RAG 服务 (:8002)         │
                                    └───────────────────────────┘

数据边界：MySQL = 用户/伴侣/对话/消息（Java 唯一写入）
          SQLite = 记忆/情绪（Python 唯一写入），关联键 userId
```

> **前端有 3 条出站链路，不是 1 条**：① `javaFetch` → Java（业务与鉴权）；② `useStreamingChat` SSE 直连 Python（聊天流式，方案 A）；③ `aiFetch` → Python（记忆/情绪读写）。三条都用 `.env` 里的 `VITE_API_BASE_URL` / `VITE_AI_BASE_URL`，无硬编码。

> 现状说明（截至 2026-11-12）：前端业务数据仍为 localStorage mock，尚未调用 Java 8080；仅 `useStreamingChat.ts` 与 `CreatePage.vue` 直连 Python 5000。Java 侧缺图片上传能力、记忆/情绪无表无接口（见 §5.2、§5.3）。打通计划见 `docs/superpowers/plans/2026-10-23-前后端打通与接后端落地.md`（含新增任务零/任务九），收敛点见 `docs/04-重构接后端收敛点清单.md`（P0-6/P0-7）。

## 🔌 三、通信与数据规范

### 3.1 基础 URL

| 用途 | URL |
|------|-----|
| 前端 | http://localhost:3000 |
| Java 业务 API | http://localhost:8080/api/v1 |
| Python AI API | http://localhost:5000/api/v1 |
| RAG API | http://localhost:8002/api/v1 |

> 已知问题：前端 `localhost:5000` 硬编码 **2 处**（`useStreamingChat.ts:3` 的 `API_BASE` 常量、`CreatePage.vue:265`），尚无 `.env` 统一配置（收敛清单 P0-4）。

### 3.2 双响应格式（保留，明确边界）

- Java：`{ "code": 200, "message": "...", "data": {...}, "timestamp": ... }`，code=200 成功
- Python：`{ "success": true, "message": "...", "data": {...}, "timestamp": ... }`

前端封装 `unwrapJava` / `unwrapPython` 统一解包，不强行统一后端格式。

### 3.3 字段命名

- JSON 一律 **camelCase**（Java DTO、Python ChatRequest 均是）
- 数据库列 **snake_case**
- Java `ConversationResponse.tags` 等为逗号分隔 String，不是数组

### 3.4 流式协议（SSE）

```
data: {"delta": "文本增量", "done": false}

data: {"delta": "", "done": true}
```

- 端点：`POST /api/v1/ai/chat/stream` 与 `/chat/langchain/stream`
- LangChain 流式为**模拟流式**（全量生成后按块切分）
- 不使用 WebSocket（历史方案已废弃，见 `AI聊天功能优化方案.md` 标注）

### 3.5 鉴权

- Java：JWT 双 Token，access 2h / refresh 7d，`Authorization: Bearer <token>`
- `JwtAuthenticationFilter` 的 principal 为 **userId 字符串**
- **放行清单**（`SecurityConfig`）：`/api/v1/auth/**`、Swagger 路径、`/uploads/**`（静态图片，`<img>` 无法带 Token，靠随机 UUID 文件名保证不可枚举）；其余一律要求认证
- Python 流式端点目前**无鉴权**（收敛点 P1-5，计划加 `X-Service-Token`）

### 3.6 验证码 mock 开关（P0-8）

- 配置项 `app.email.mock`，**代码兜底默认 `false`**，仅 `application.yml` 显式写 `true` 时启用。
- mock 模式：验证码固定 `123456`，存进程内 Map（**不依赖 Redis**），`/auth/send-email-code` 响应 `data.code` 带回码。
- 真实模式：走 Redis（5 分钟 TTL）+ 控制台打印；真实邮件服务**尚未接入**（`AuthServiceImpl` 内有 TODO）。
- 生产部署必须确保 `app.email.mock: false`，否则全站验证码恒为 `123456`。

## 🗄️ 五、数据层

### 5.1 存储一览

| 服务 | 存储 | 实际表 |
|------|------|--------|
| Java | MySQL 库 `ai_companion` + Redis（真实验证码）+ 本地 `uploads/` | **5 张**：`user` / `companion` / `user_companion` / `conversation` / `message`（含 `images`） |
| Python | SQLite `ai_companion.db` + Chroma + `chroma_db/` | **仅 2 张**：`user_memories` / `user_moods`（死模型已于 2026-11-12 删除） |
| RAG 8002 | MySQL 库 `rag_knowledge` + `storage/chroma_db/` | 知识库 / 文档 / 切片 / 伴侣绑定 |

预置数据：4 个系统伴侣（preset-1 小暖 / preset-2 小智 / preset-3 小甜 / preset-4 小酷，dicebear 头像），由 `schema.sql` 初始化。

> ⚠️ **v3.0 文档写的"MySQL 6 张表含 user_memories / user_moods"是错的。** Java 侧从未建这两张表，也没有对应 entity / mapper / controller。

### 5.2 数据归属边界（2026-11-12 决策）

这是本架构最容易踩坑的地方：**两套数据库按"业务域"切分，而不是按"服务"切分**，且不做双写同步。

| 数据域 | 权威存储 | 唯一写入方 | 读取方 |
|--------|----------|-----------|--------|
| 用户 / 伴侣 / 收藏 / 亲密度 / 对话 / 消息 | MySQL | Java 8080 | Java → 前端 |
| 用户记忆 / 情绪 | SQLite | Python 5000 | Python（AI 工具直接读写）+ 前端 |
| 知识库 / 文档 / 向量 | MySQL `rag_knowledge` + Chroma | RAG 8002 | Python 5000 代理调用 |

- **唯一关联键是 `userId`**（Java 生成的 UUID 字符串，`VARCHAR(36)`；Python 的 `user_memories.user_id VARCHAR(50)` 足够容纳）。
- 两个库**不互相同步**，也没有分布式事务。记忆丢失不影响聊天；反之亦然。
- 为什么这样切：记忆/情绪被 LangChain 的 `search_user_memory` / `add_user_memory` / `get_mood_history` 三个工具直接读写，移到 MySQL 需要 Python 走 HTTP 调 Java，每轮对话多一次网络往返且增加故障点。短期保留 Python 权威，长期若要统一再评估。

### 5.3 图片存储（2026-11-12 决策，后端已实现）

- **头像与聊天图片一律存 URL，不存 base64。**
- `companion.avatar` 保持 `VARCHAR(500)`（存 URL 足够）。
- `message.images`（TEXT，**已加列**）存 URL 的 JSON 数组字符串，如 `["http://localhost:8080/uploads/2026-11/xxx.jpg"]`。Java 侧保持字符串形态不反序列化，前端自行 `JSON.parse`（与 `tags` 口径一致）。
- 上传端点：`POST /api/v1/uploads`，body `{ "dataUrl": "data:image/png;base64,..." }` → `data: { "url": "..." }`。
  - 白名单 MIME：jpeg / jpg / png / webp / gif；上限 5MB；
  - 落盘 `{app.upload.dir}/{yyyy-MM}/{uuid}.{ext}`；
  - 配置项：`app.upload.dir` / `app.upload.base-url` / `app.upload.max-size`。
- 静态访问：`WebConfig.addResourceHandlers` 把 `/uploads/**` 映射到该目录，**必须用绝对路径的 `file:` URI**（`Paths.get(dir).toAbsolutePath().normalize().toUri()`），否则会按 classpath 解析导致 404。
- **安全边界**：`/uploads/**` 在 `SecurityConfig` 中 `permitAll()`——`<img>` 标签无法携带 Authorization 头；安全性由文件名中的随机 UUID 保证（不可枚举）。上传端点本身仍需 JWT。
- 前端 base64 只用于**发送前的本地预览**，任何落库动作前必须先换成 URL。
- 二期可换对象存储，只需替换 `FileService` 实现，接口不变。
- 老库升级：`CREATE TABLE IF NOT EXISTS` 不会自动加列，需手动执行 `backend-java/src/main/resources/migration.sql`。
