## 1. 产品定位与设计原则

**RAG 知识库在产品中的角色**：AI 伴侣的"角色脑内知识"。主应用的伴侣有人设（伴侣广场 4 位预设 + 用户自建），聊天时 LangChain Agent 通过 `search_knowledge` 工具检索该伴侣的知识库，把角色设定、背景故事、说话风格、口癖等知识注入回答——让伴侣"知道自己是谁、喜欢什么、经历过什么"，而不只靠系统提示词里的几句话。

四条设计原则：

1. **伴侣级隔离**：一切知识以 `companionId` 归属，检索按伴侣路由，A 伴侣的知识绝不进 B 伴侣的回答；
2. **契约兼容**：5000 → 8002 的 `/api/v1/kb/retrieve` 契约不破坏，主应用零改动受益；
3. **账号即主应用账号**：不建新用户体系，RAG 登录 = 主应用登录；
4. **从现有功能反推知识需求**：知识内容围绕"让聊天更懂角色"设计，不做通用文档平台。

## 2. 现有功能 → RAG 支撑关系

主前端（`frontend/`，端口 3000）实读页面：HomePage（首页）、SquarePage（伴侣广场）、CreatePage（创建/编辑伴侣）、ChatPage（聊天核心页）、HistoryPage（聊天记录）、MemoryManagement（记忆）、EmotionCalendar（情绪）、NotesPage（笔记）、ProfilePage（个人页）、LoginPage。

| 现有功能 | 与 RAG 的关系 | 说明 |
| --- | --- | --- |
| 聊天（ChatPage） | **核心受益方** | `enableRAG` 开关（默认开）决定走 LangChain 增强链路；Agent 的 `search_knowledge` 工具调 8002 retrieve，命中知识拼接进回答 |
| 伴侣广场 / 创建编辑伴侣（SquarePage / CreatePage） | 知识库的"宿主" | 每个伴侣（`preset-1~4` 预设 / UUID 自建）可绑定知识库；RAG 前端按伴侣筛选与检索 |
| 聊天记录（HistoryPage） | 无直接关系 | 对话落库 Java，不进知识库（📋 "从聊天沉淀知识"为候选） |
| 记忆（MemoryManagement） | **明确边界外** | 用户本人记忆走 5000 本地向量（`search_user_memory` / `add_user_memory`），不迁 RAG |
| 情绪（EmotionCalendar） | 边界外 | 情绪存 MySQL，`get_mood_history` 工具，与知识库无关 |
| 笔记（NotesPage） | 边界外，候选来源 | 笔记存 Java；📋 "笔记转知识"为候选 |

## 3. 用户角色与使用场景

一套账号、三种使用姿态：

1. **聊天用户（被动受益）**：不接触 RAG 前端，只在聊天中获得更懂角色的回答；
2. **知识管理员 = 同一用户（主动运营）**：在 3001 前端维护知识库（上传设定文档、写手动知识、检查召回效果）；
3. **系统服务（Python 5000）**：X-Service-Token 服务间调用，检索完全自动化，用户无感。

典型场景：

- **场景 A · 新建伴侣**：用户在主应用捏了新伴侣"小暖" → 到 3001 登录 → 新建知识库绑定"小暖" → 上传《人物设定.md》+ 手动写"口头禅：比想象中顺利" → 任务进度 100% → 回主应用聊天，小暖能用设定内容回答；
- **场景 B · 双工具命中**：用户问"你上周担心的问题他们问到了吗" → Agent 同时判断走 `search_user_memory`（本人记忆）与 `search_knowledge`（伴侣知识）→ 回答引用了知识库里的面试问题清单；
- **场景 C · 知识更新**：设定变了 → 管理员重索引文档或删除重传 → 聊天即用新知识（手动知识编辑入口见 F2.3 现状标注）；
- **场景 D · 效果调试**：管理员在检索调试页以用户视角提问，查看命中切片与得分，发现召回差 → 更换/补充文档或调阈值。

## 6. 页面交互设计（3001，与已实现代码对齐）

### 6.1 登录页
- 输入：邮箱 + 密码（非空校验，回车提交）；成功 → `/collections`；失败 → toast 错误信息；
- 全局：401 拦截自动清 token 跳登录；已登录访问 /login 自动跳知识库列表。

### 6.2 知识库列表页
- 筛选区：名称搜索（回车/清除/按钮触发）、角色下拉筛选、查询按钮；
- 表格列：名称、描述（溢出省略）、文档/切片数、向量配置（模型·维度·后端）、状态、操作（详情/编辑/删除）；
- 新建/编辑模态：名称（必填 ≤100 计数）、描述（textarea）、绑定角色（下拉，可清空）；
- 删除：二次确认，文案明示"文档、切片与向量会一并删除"；分页 10/页。

### 6.3 知识库详情页
- 页头：返回 + 知识库名 + 向量配置摘要（模型·维度·后端·切片 500/50）；
- 上传卡：拖拽多选（accept 限 .json/.md/.txt）→「上传并解析」提交 → toast 任务数 → 2s 轮询全部任务至终态 → 刷新列表并 toast 成败（失败显示 errorMsg）；
- 手动写知识模态：标题（必填 ≤255 计数）+ 内容（必填 textarea）→「提交入库」；
- 文档表：标题、来源（sourceType）、状态（tag 色映射）、进度%、切片数、错误信息、更新时间、操作（重索引/删除，删除二次确认）；
- 🔧 待补（F2.3）：manual 文档的「编辑」按钮 + 编辑模态（标题/内容），保存后触发重建索引并轮询。

### 6.4 检索调试页
- 范围切换：按角色（单选）/ 按知识库（多选，塌缩展示）；
- 参数：topK（1–20）、分数阈值（0–1，步长 0.05）；
- 查询输入（回车检索）；结果区：命中数、耗时 ms、检索知识库数；每条命中卡片：score（4 位小数 tag）、文档名、知识库名、切片序号、原文（保留换行）；零命中空态提示。

## 7. 核心业务流程

### 7.1 入库流水线
```
上传/手动知识 → 保存 storage/uploads（仅文件）→ 解析（json 按 parserConfig；md/txt 直读）
→ 切片（500 字 / 重叠 50）→ 写 MySQL（kb_document / kb_chunk）
→ 向量化 + 写向量库（✅现为 Chroma 哈希 256 维 → 🔧 Phase 1–3：Milvus Function 服务端调智谱 Embedding-3，8002 只传文本）
→ 任务终态（progress=100 / status=completed）
```

### 7.2 聊天检索链路
```
用户消息 → 5000 LangChain Agent → 工具判定：
  本人记忆/聊天历史 → search_user_memory（本地向量，不走 8002）
  伴侣设定/背景     → search_knowledge → POST 8002 /api/v1/kb/retrieve（{companionId, query, topK:4}，超时 3s）
      命中   → 拼接 content 注入回答
      零命中 → 返回提示语（正常业务，不降级）
      超时/异常/5xx/4xx → 回落本地 RAGStore 兜底
```

### 7.3 登录链路
```
3001 提交邮箱密码 → 8002 POST /api/v1/auth/login（转发）→ 8081 BCrypt 校验
→ 签发 JWT（access 2h / refresh 7d）→ 8002 归一化 {success, data: AuthResponse}
→ 3001 存 localStorage → 后续请求自动带 Authorization: Bearer（🔧 Phase 2 起 8002 强制验签）
```

## 8. 数据与规则细节

| 项 | 规则 |
| --- | --- |
| 切片 | 默认 500 字 / 重叠 50；创建时 API 可调（chunkSize 50–2000、chunkOverlap 0–500），前端本期未暴露高级参数 |
| 上传限制 | json / md / txt，单文件 ≤20MB，支持多文件 |
| 级联删除 | 知识库 → 文档 → 切片 → 向量（向量化后含 Milvus 侧），全部软删（MySQL）+ 硬删（向量库） |
| 归属与防探测 | 他人资源统一 400/403，不区分"不存在"与"无权"（沿用主后端口径） |
| 空结果语义 | 检索成功但零命中 = 正常业务结果，返回提示语，**不触发降级** |
| 性能预算 | 检索端到端 ≤3s（RAG_TIMEOUT=3s）；F4.4 引入 rerank 往返后如超预算 → 压测校准阈值或放宽 timeout（技术方案 §12.3） |
| 并发安全 | companionId 检索按请求构建 agent（闭包绑定），现有行为不变 |

## 9. 非功能需求

- **性能**：retrieve P95 ≤ 1.5s（Phase 2 接入 rerank 后压测校准）；入库为异步流水线，20MB 文档的解析/切片/向量化全程进度可见；
- **可用性**：8002 整体不可用时聊天不挂（本地降级链）；Milvus 不可用时 8002 返回明确错误（不静默吞掉）；
- **安全**：JWT_SECRET / 智谱 key / Milvus 凭证全走 `.env` 与 gitignore 文件，文档一律 `sk-***` 占位；Milvus 开启 RBAC 专用账号（技术方案 §9）；
- **容量估算**（本机自用规模）：伴侣 ~10、知识库 ~10、文档百级 → 切片万级向量，2048 维 ≈ 8KB/条 → 向量数据 ~80MB，Milvus Standalone 单机绰绰有余。

## 10. P0 验收标准（可直接当测试用例）

1. **登录**：主应用账号在 3001 登录成功进列表；错误密码 toast 失败；未登录直访受限页跳登录；token 过期自动回登录页；
2. **知识库 CRUD**：新建绑定"小暖" → 列表可见 → 编辑名生效 → 删除后文档/切片级联消失；
3. **文件上传**：3 个 md 一次上传 → 任务进度推进 → 终态 completed、切片数 > 0；错误文件给 errorMsg；
4. **手动知识**：录入 → 入库 → 检索调试页命中该内容与得分；
5. **更新与删除**：重索引后命中新内容；删除文档后不再命中；
6. **伴侣隔离**：按 companionId 检索只命中该伴侣绑定的知识库；换伴侣检索零命中；
7. **聊天集成**（Phase 4 后）：开 enableRAG 问设定相关问题，回答包含知识库内容；停 8002 后聊天仍可用（降级链生效）；
8. **工具选择双向回归**（CLAUDE.md 规则）：问"我上次说过什么"走 `search_user_memory`；问"你的性格设定"走 `search_knowledge`；
9. **鉴权**（Phase 2 后）：无 token 访问管理接口 401；他人 companion 资源 403/400；X-Service-Token 错误 retrieve 401；
10. **Milvus 升级回归**：上述用例全部重跑 + Milvus WebUI（9091）可见知识向量集合。
