## Decisions Made

- **P0-5 采用方案 A（前端直连 Python 流式 + 流结束回写 Java 落库）** —— 理由：保留逐字体验和三层降级链，不用在 Java 端新造 SSE 转发；方案 B（Java `StreamingResponseBody` 透传）多一跳延迟，列为二期。
- **P1-3 不做格式统一（保留 Java `code` / Python `success` 双轨）** —— 理由：改动面大、收益低；靠前端两个 unwrap 函数隔离，业务代码不裸摸 `res.data`。
- **P1-4 JSON 一律 camelCase，DB 列 snake_case** —— 理由：与现有 Java DTO 和 Python `ChatRequest` 一致；旧文档的 snake_case 是错的。`tags` 明确为逗号分隔 String，不擅自改成数组。
- **P2-3 本轮不用 WebSocket** —— 理由：SSE 已落地，Java 的 WS 配置无业务端点、前端无连接代码。
- **P1-2 第 6 项 `PRESET_RESPONSES` 明确保留** —— 它是三层降级链第 3 级（兜底），不是假数据；只需在响应里标 `source: "preset"`。
- **P1-1 RAG 短期只做代理** —— `search_knowledge` 优先打 8002，本地 `RAGStore` 降为兜底；删除主服务内建向量导入路径列为长期。
